Public Sector Data Quality Commons

A free, open hub and toolkit for everything about data quality in the public sector: check data, find the frameworks and standards that apply, learn, use AI safely, and share what works. For central and local government, the devolved governments, the wider public sector, the voluntary and private bodies that deliver public services, and the Crown Dependencies, Overseas Territories, Commonwealth and international partners the UK works with.

For beginners

What it is. One shared place to check whether data is good enough to use, learn how to improve it, and see which frameworks and standards apply to you. Read why it exists, its aims and desired outcomes on the About page.

What GitHub is, and why the Commons lives here. This page is the project's repository: the files the portal is built from, with every past version and an open noticeboard. You don't need to code. Our plain-English introduction to GitHub explains the words you'll see (issue, pull request, release) and what you can do at each level.

Things you can do today, in your browser:

  1. Check a CSV file against quality rules. Nothing is uploaded.
  2. Follow the learning pathway for your role.
  3. See where data quality sits in your profession's skills framework.
  4. Find frameworks and standards for your nation or sector.

Report a problem or suggest an idea: open an issue (a free GitHub account is needed), or use the help routes if you'd rather not. Never post personal data or anything sensitive: everything here is public.

Quick start on your own computer (copy and paste, no coding)

  1. Install Python 3.10 or later.
  2. In a terminal, in this folder, run: pip install -r requirements.txt
  3. Check the kit works: python -m unittest discover -s tests You should see OK at the end (131 tests at the time of writing). python scripts/parity_check.py also proves the browser version gives the same answers (37 cases).
  4. Check a data file against a rules file: python -m dqkit check assessments/ndl/chart-data/people__births.csv rules/ndl/births.yaml --out my-results You get a plain summary on screen, plus these files in my-results/:
  5. *.results.json: every rule, pass rate, and priority
  6. *.dqv.jsonld: results as W3C Data Quality Vocabulary metadata, ready for a catalogue
  7. .dqap-rules.csv and .dqap-issues.csv: rows to paste into the GOV.UK DQAP template Add --workbook to also get a filled-in DQAP Excel workbook. It has 11 tabs: Start here, Details, Criticality matrix, Metrics, Results, Issues log, Causes, Actions, Operations, RACI and Steps. Add --history my-history to keep every run, so the Results tab shows the trend over time, and the Issues log shows how long each issue has been open and which are overdue (escalate). Add --case-study to draft a case study (.md and .docx). The summary also gives a suggested trust level (adapted from the IOPC's data trust scales: Untrustworthy, Requires improvement, Useable, Trustworthy) and the DQAP route for internal or external data.
  8. Turn the same rules into another tool's format:
  9. Great Expectations: python -m dqkit export rules/ndl/births.yaml --to gx
  10. R validate: python -m dqkit export rules/ndl/births.yaml --to r-validate
  11. Re-run the NDL assessment: python scripts/run_ndl_assessment.py
  12. Measure a whole portfolio of assets in one go (what the weekly automated pipeline does): python -m dqkit run portfolio.ndl.yaml --out assessments/portfolio Read assessments/portfolio/run-summary.md for a plain-English digest. It also writes portfolio.json (for the web portal), escalations.json (overdue Critical and High issues), one merged DQV catalogue file, and every asset's workbook, CSVs and case study. Add --as-of YYYY-MM-DD to measure as if on a date, and --fail-on-escalation to finish with exit code 2 when something needs escalating. See docs/OPERATIONS.md.
  13. Start a rules file for a new data file: python -m dqkit suggest my-data.csv --title "My data" --owner "My Department" --out rules.yaml This drafts rules from what the data looks like. A data steward must review every rule.
  14. Build the portal from the latest results: python scripts/build_dq_portal.py (writes portal/dist/). Every page is a static file; open portal/dist/index.html in a browser.
  15. Install the dqkit command (optional): pip install -e . then run dqkit check ... instead of python -m dqkit check ....

Writing a rules file

asset:
  id: my-asset            # short, unique
  title: My critical data asset
  owner: My Department
  importance: 3           # GOV.UK issues framework: 1 Low, 2 Medium, 3 High, 4 Critical
rules:
  - {id: R1, check: not_null, column: nhs_number}
  - {id: R2, check: unique, columns: [nhs_number]}
  - {id: R3, check: regex, column: postcode, pattern: '[A-Z]{1,2}\d[A-Z\d]? ?\d[A-Z]{2}'}
  - {id: R4, check: freshness, column: extract_date, expected: P1M, lag: P7D}
  - {id: R5, check: not_unknown, column: ethnicity}            # inclusion check
  - {id: R6, check: group_disparity, group: sex, tolerance: 5,
     inner: {check: not_null, column: nhs_number}}            # is quality equal across groups?

Optional asset fields:

  • source (internal or external) and influence (true or false): choose the decision-tree route.
  • target_policy (low, mid or high): sets default targets.
  • personal_data_columns: used by the personal data accuracy rule in the trust level.
  • primary_use, secondary_uses and steward: fill the Details tab.

Optional rule fields:

  • purpose, requirement, method and notes: fill the Metrics tab, matching the Defra and DQAP rule templates.
  • personal_data: true: marks a personal data field.
  • control_point (source, pipeline or reporting): where the control that prevents this failure belongs. The default comes from the check type.

Checks available: not_null, required_columns, unique, type, regex, in_set, range, not_future, compare, sum_max, freshness, no_gaps, header_has_unit, not_unknown, group_disparity, identifier and outlier (valid but implausible numbers: method: iqr with k, default 1.5, or method: zscore with threshold, default 3). Each maps to an issue type in vocab/issue-types.csv. You can override a rule's impact (1 to 4), target (%), dimension or issue_type.

How scoring works

The kit applies the published data quality issues framework exactly: importance × impact sets a target range; performance below target falls into a band; importance × impact × band gives the priority (Low, Medium, High, Critical) and the time to fix. The tests check the kit against the framework's own worked example.

Background and evidence

Headline findings from the NDL assessment (14 October 2026)

  • 84 curated data pages in 7 collections were tested against 20 checks drawn from the DAM policy, CDA metadata guidance, DQAP guidance, NDL curation criteria, FAIR principles and inclusion.
  • Average score: 50.9%. 1 page green, 47 amber, 36 red.
  • Average coverage of the 13 CDA metadata properties: 46.4%.
  • Strong: every page was reviewed in the last 12 months. Only one factual error was found. 91% name the provider and link to authoritative sources.
  • Weak: no page shows an accountable owner role or a security classification. Only 1 links a methodology, and 56 of 84 give no quality information at all. 32% state an update frequency. 11% declare a schema.
  • 8 chart data files were checked with 49 rules. Main issues: air quality chart missing 2025, unclear measures (vaccinations, council tax), and missing context columns (election, social mobility).
  • One factual error found: the Driving tests page says "Driver and Vehicle Standards Agency (DVLA)".

Full report: assessments/ndl/REPORT.md.

Product requirements (PRD)

Product requirements: NDL data quality assurance kit

Problem

Departments must report a data quality baseline for every critical data asset (CDA) in their first return under the data asset management policy. The GOV.UK DAM policy also requires a DQAP or equivalent for each asset. But:

  • departments mostly build their own checking tools (Public Sector DQ Tooling Atlas, October 2026)
  • there is no shared issue vocabulary
  • the cross-government metadata model has no field for quality
  • the NDL's own pages don't yet show the metadata the policy asks for (assessment, 14 October 2026)

Users and needs

UserNeed
Data steward in a department or ALBMeasure the quality of my asset quickly, in a way GDS will accept, without buying a tool
Data owner (senior)See which issues matter most and how fast they must be fixed
GDS / NDL catalogue teamReceive quality results in a standard, machine-readable form; show them to users
CDO CouncilSee quality across government and where help is needed
Data user (public, researcher, journalist)Know whether data is fit for my purpose, and for which groups of people

Requirements (MoSCoW)

Must:

  1. Apply the GOV.UK issues framework exactly (importance, impact, targets, bands, priority, timescale).
  2. Cover the six DAMA UK dimensions, plus inclusion (representativeness).
  3. Output rows for the GOV.UK DQAP template.
  4. Output W3C DQV metadata.
  5. Assess catalogue records against the DAM policy and CDA metadata guidance, with every check citing its source.
  6. Run without paid software; MIT licence.
  7. Explain results in plain English.

Should:

  1. Export to Great Expectations and R validate.
  2. Offer a shared issue vocabulary as SKOS.
  3. Propose a quality extension to the metadata model.
  4. Run in CI.

Could:

  1. Connectors for databases and Spark.
  2. A web form for non-technical stewards.
  3. Publish to Purview or Dataverse.

Won't (this release):

  1. Store or process personal data centrally.
  2. Replace departmental tools.

Success measures

  • A steward with no prior experience can run a first baseline in under one hour (to test in user research).
  • 100% of the issues framework's published examples are reproduced by the tests (achieved: tests pass).
  • The NDL page template gains the missing metadata fields, and the average NDL score rises from 50.9% to over 75%.
  • At least 3 departments use the vocabulary or kit for the January return.

Out of scope / constraints

  • Data stays with its owner. The kit runs where the data is.
  • Only OFFICIAL data, matching DAM policy scope.

Equality and data protection screening

Equality and data protection screening

Data protection (DPIA screening)

  • Personal data processed by this repository: none.
  • The NDL harvest holds page metadata only, with organisation names.
  • Chart data is aggregate statistics.
  • The kit itself runs where the data lives and stores nothing centrally.
  • When departments use the kit on personal data:
  • Failing-row examples (up to 5 values per rule) may contain personal data.
  • Keep results inside the department, or share only the DQV and DQAP outputs, which hold rates, not records.
  • The department's existing DPIA for the asset covers this processing.
  • Conclusion: a full DPIA is not needed for this repository. Review this if a hosted service is built.

Equality (public sector equality duty, Equality Act 2010 s.149)

Who could be affected:

  • people under-recorded in data, such as some ethnic groups, disabled people, people with no fixed address and digitally excluded people
  • users of assistive technology
  • people in the devolved nations

Positive measures built in:

  • Representativeness dimension and 4 inclusion issue types. Covers characteristic missing or defaulted, group disparity and undercoverage.
  • not_unknown and group_disparity checks. These test whether quality is equal across groups, not only overall.
  • NDL checks INC-1 (breakdowns stated) and INC-2 (other nations signposted). FAIR-1 also flags data that isn't machine-readable, because it is harder for assistive technology users.

Risks and mitigations:

  • Risk: inclusion checks need protected-characteristic fields, and collecting more such data has its own risks. Mitigation: the kit measures what exists. It doesn't require new collection. GSS harmonised standards are recommended where data is collected.
  • Risk: scores may be read as judgements about groups of people. Mitigation: results describe data quality only. Reports use neutral language.

Accessibility of outputs:

  • Plain-English summaries.
  • HTML artefacts built to WCAG 2.2 AA intent (contrast, keyboard focus, reduced motion).
  • Not yet tested with assistive technology users. That testing is in the research plan.

3. Low-level design (LLD)

Scoring flow for one rule

  1. Pass rate = records passing ÷ records checked × 100.
  2. Combined score = asset importance (1–4) × rule impact (1–4). The impact defaults from the issue type.
  3. Target = the rule's own target, or the default for the framework range: 85, 95, 99 or 100.
  4. If below target, find the band:
  5. Middle band starts at 100 − 2 × (100 − target).
  6. High band starts halfway between the middle-band start and the target.
  7. Score: Low 3, Middle 2, High 1, and 4 when the target is 100.
  8. Priority score = importance × impact × band score:
  9. 1–7 Low
  10. 8–16 Medium
  11. 17–32 High
  12. 33–64 Critical
  13. Resolution comes from Table 8.

Control points and escalation

  • Each rule has a control_point: source (capture), pipeline, or reporting. It defaults by check type.
  • An issue's age is the number of consecutive measurement cycles below target, read from the history.
  • An issue is overdue when its age exceeds its priority's window: Critical 1, High 1, Medium 3, Low 6 (D-026).

Dataset-level checks

freshness, sum_max and group_disparity give one pass or fail (checked = 1). freshness treats a year label as covering the whole year. It passes when (as_of − end of the latest period) ≤ expected frequency + lag.

Reading numbers and outliers

Numbers are read by dqkit/numbers.py (mirrored by pdNumber in engine.js), not by pandas, so results do not change with the pandas version (D-TK-02). outlier counts only cells that are numbers; blanks and text are left to not_null and type. With method: iqr a value fails outside Q1 − k·IQR to Q3 + k·IQR (numpy's linear quantile, written out in both engines); with method: zscore it fails more than threshold sample standard deviations from the mean. Fewer than 4 numbers: nothing to compare, so every value passes.

6.3 Low-level design (LLD)

Metadata Weaver (dqkit/weaver.py, DQ.weaver).

  1. detect(record): ODCS if kind: DataContract or apiVersion; DCAT if a dcat: type, context or key; schema.org if @type: Dataset; CKAN if package keys (also inside an API result).
  2. read_<format> fills a canonical record of 22 fields (FIELDS: key, label, Rosetta concept, CDA property, which outputs carry it). Lists are de-duplicated; nothing is inferred.
  3. to_dcat, to_schema, to_ckan, to_odcs write only filled fields. DCAT uses dqc: for security classification and expiry. ODCS needs an id and version, so it uses visible placeholders (dataset, 1.0.0).
  4. coverage() lists filled, missing and "not carried" fields per output; cda_check() scores the 13 CDA properties (description needs 40 characters; distributions need a format) with half credit for partial.

Contract change control (dqkit/contracts.py).

  • validate_odcs: errors for missing required fields, wrong kind, unnamed schema objects or properties, repeated property names; warnings for non-v3, unknown status, non-semantic version, no schema, unknown metrics, rules without thresholds, no team, no SLA.
  • diff_odcs: columns keyed by (object, property). Breaking: removed column, changed type, lost required or unique, removed quality rule, looser threshold, status moved to deprecated or retired. Suggests major, minor or patch; version_ok says whether the stated version is a big enough bump.

Content health (scripts/self_check.py). Eight checks, each finding an error, warning or note; writes health.json and health.md; exit 1 on errors (or warnings with --strict). The build embeds a summary in Help us build this. The weekly workflow keeps one GitHub issue open while there are findings.

Contact and moderation. The sender's message is an item of kind contact in their own queue/{uid} document (rules: owner read and write, editors read all). Moderators reply in place (status: answered, reply), which the sender sees on Help us build this. No email field exists.

Provenance. At build time each page's __K_NAME__ placeholders are mapped to knowledge files; the oldest review.last_reviewed and the owning roles are printed above the colophon.

Backlog to issues. Idempotent: existing issues are matched by [BL-nn]. Items with a Jira key get jira-linked, which the Jira sync workflow skips.

Operations

Operations runbook: the data quality pipeline

This runbook is for the people who look after the pipeline day to day. You do not need to be a developer. Where you need to type a command, it is shown in full, ready to copy and paste.

Status: untested on GitHub. The two workflow files (.github/workflows/dq-pipeline.yml and .github/workflows/ci.yml) have been checked by the kit's tests (their structure and required settings), but GitHub Actions cannot run until the repository is pushed to GitHub. Expect to fix small problems on the first real run. Everything else in this runbook (dqkit run, dqkit suggest, the output files) has been run and tested locally.

1. What the pipeline does

Once a week (Monday, 06:17 UTC), GitHub runs the pipeline for you. It:

  1. Checks the kit works by running the automated tests. If they fail, it stops, so it never publishes wrong results.
  2. Measures every asset listed in the portfolio file (portfolio.ndl.yaml): it runs each asset's rules file on its data file, scores the results with the GOV.UK data quality issues framework, and works out a trust level, the DQAP route, and how long each issue has been open. Assets with a schedule are only re-measured when they are due (see section 6).
  3. Assesses the catalogue records (the 84 NDL data pages) against GOV.UK requirements.
  4. Saves the results back into the repository, but only if something really changed.
  5. Raises escalations as GitHub issues: one issue per asset and rule. It comments on an issue that is still open, and closes issues that are now fixed.
  6. Publishes the NDL Data Quality Portal to GitHub Pages. scripts/build_dq_portal.py builds it from this run's results into portal/dist/.

2. How to switch it on (once the repository is on GitHub)

You need to be an administrator of the repository.

  1. Push the repository to GitHub (the lead does this).
  2. Turn on Actions. Go to the repository's Settings → Actions → General. Under "Actions permissions", choose Allow all actions and reusable workflows. Under "Workflow permissions", choose Read and write permissions, so the pipeline can save results and open issues.
  3. Turn on GitHub Pages. Go to Settings → Pages. Under "Build and deployment", set Source to GitHub Actions. (Not "Deploy from a branch".) Two workflows publish the portal: publish portal (pages.yml) on every push to main, and the weekly pipeline after it refreshes results. The build bundle is published at /bundle/. Releases: pushing a tag such as v1.5.0 runs release (release.yml), which checks the version is in knowledge/releases.yaml and creates the GitHub release with notes and a source zip.
  4. Issue label. The pipeline creates the dq-escalation label itself the first time it needs it. If you want to create it by hand: Issues → Labels → New label, name dq-escalation.
  5. Run it once by hand to check it works: Actions → Data quality pipeline → Run workflow. Leave the date blank for today. Watch the run; every step has a plain-English name.

4. How to add an asset to the portfolio

  1. Put the data file in the repository (for example assessments/ndl/chart-data/my-file.csv).
  2. Write a rules file for it, or draft one with dqkit suggest (section 5).
  3. Add one line under assets: in portfolio.ndl.yaml: ```yaml
  4. {rules: rules/ndl/my-asset.yaml, data: assessments/ndl/chart-data/my-file.csv, schedule: quarterly, tags: [people]} ```
  5. schedule is optional: weekly, monthly, quarterly or annual. Leave it out to measure on every run.
  6. enabled: false pauses an asset without deleting it.
  7. Check it: python -m dqkit run portfolio.ndl.yaml --out /tmp/try-it. If something is wrong you get a message such as Asset 9 (rules/ndl/my-asset.yaml): the data file 'my-file.csv' was not found.
  8. Commit the data file, the rules file and the portfolio change together.

The portfolio file is checked against dqkit/portfolio.schema.json. History is kept in the history_dir folder, which is inside the output folder (assessments/portfolio/history).

5. How to start a new asset with dqkit suggest

dqkit suggest looks at a data file and drafts a rules file for you:

python -m dqkit suggest assessments/ndl/chart-data/people__births.csv --title "Births" --owner "Office for National Statistics" --out rules/ndl/my-births.yaml

It looks at each column (missing values, number of different values, whether it holds years, dates, numbers, a short list of codes, or UK geography codes such as E06000001) and suggests:

  • required_columns for all columns, and not_null for columns that are almost never empty
  • unique for the probable key (a column, or pair, that never repeats)
  • type for numbers, years and dates; in_set for short code lists; regex for geography codes
  • no_gaps and freshness for years and periods (expected: P1Y, which you must confirm)
  • header_has_unit for measure columns (this one often fails: it is a real, common issue)
  • not_unknown, and a commented-out group_disparity example, when a column looks like a personal characteristic (sex, gender, ethnicity, age, disability, religion), as an inclusion prompt

The draft is designed to pass on the data it came from ("green, then tighten"). A data steward must review it: replace every [steward to confirm] with the rule's purpose, confirm importance and the freshness settings, delete rules that do not matter, add business rules (ranges, comparisons), and tighten.

6. What "due", "open" and "overdue" mean

  • Measurement cycle: one measurement of an asset. With schedule: quarterly, the weekly pipeline measures the asset about every 13 weeks; in between, it carries the last result forward and does not count a new cycle. (Due after: weekly 6 days, monthly 28, quarterly 89, annual 364.)
  • Open: a rule is below its target. "Cycles open" is how many measurements in a row it has been below target.
  • Overdue: open for longer than the GOV.UK data quality issues framework allows for its priority:
PriorityFramework resolutionOverdue when open for more than
CriticalImmediately1 cycle (the kit treats "immediately" as "by the next measurement")
HighWithin 1 measurement cycle1 cycle
MediumWithin 3 measurement cycles3 cycles
LowWithin 6 measurement cycles6 cycles

7. What happens on escalation, and who acts

An issue is escalated when its priority is in notify.escalate_priorities (Critical and High for the NDL portfolio) and it is overdue. (Set notify.escalate_when: open to escalate as soon as such an issue appears.)

For each escalation the pipeline opens one GitHub issue, titled [DQ] <asset id> <rule id>: <issue> (<priority>), labelled dq-escalation. The body says, in plain English, what failed, the performance against the target, how long it has been open, who acts, and the suggested next step. On later runs it adds a comment (once per new measurement). When the rule meets its target again, it closes the issue with a comment. If it comes back later, a new issue opens and the kit counts it as a recurrence.

Who acts depends on the DQAP route (from the 2023 decision tree, set in the rules file by source and influence):

RouteWho actsWhat they do
Internal dataData owner, and the governance board when Critical or High is overdueFix the root cause in your own process or system; record cause and action in the DQAP workbook
External data, some influenceData owner (and governance board), working with the supplierAgree the fix with the supplier; record it in the DQAP actions
External data, no influence (all NDL charts today)Data owner (and governance board) records and communicates; the supplier fixesTell the supplier, caveat the data for users, record the limitation in the metadata and DQAP

Whoever is assigned the GitHub issue should: open the asset's DQAP workbook (assets/<id>.DQAP.xlsx), fill in the Causes and Actions tabs, and close the loop at the next measurement.

8. Known limits

  • Data files are local. The pipeline measures the files that are in the repository. It does not download fresh data from the source.
  • No automatic refresh yet. A scheduled run re-measures the same files unless someone updates them. Only time-based rules (freshness, not_future) change on their own as the date moves on.
  • Proposed refresh step. Add an optional source_url to each asset in the portfolio file and a new workflow step, before "Measure the portfolio", that runs a small scripts/refresh_data.py:
  • download each source_url to a temporary file;
  • check it is a CSV that pandas can read and that it still has the columns the rules file needs (the required_columns rule);
  • only then replace the file in the repository, and record the download date and a checksum in assessments/portfolio/sources.json (provenance);
  • if a download fails, keep the old file and record the failure, so the run still completes and the freshness rule shows the data is getting old. The refreshed files are then committed with the results, so every result can be traced to the exact data measured.
  • Pages and issues need GitHub settings (section 2). Without them the run still measures and saves results, but those steps fail.
  • History lives in the repository. If two people run the pipeline into assessments/portfolio with different dates and both commit, merge the history CSVs carefully (each row has a date).
  • Size. catalogue.dqv.jsonld is about 2.4 MB because it includes the 84 catalogue pages.

  2. Weekly triage (30 minutes, open notes). Each item gets one label: backlog, answered, community, specialist or declined (with the reason).
  3. Backlog. The backlog label mirrors the issue to Jira automatically (.github/workflows/backlog-sync.yml): a story is created under epic XDMH-210 and its key is commented back on the issue. GitHub stays the place for discussion; Jira is the plan.
  4. Prioritisation (monthly). Score = user value x reach x inclusion benefit / effort. Items that help people who are often left out of data, or that fix accessibility, go first when scores tie.
  5. Build. A pull request using the template. It must pass tests, the Python and browser parity check, and the accessibility checks. Docs change in the same pull request.
  6. Release. Merge to main runs the pipeline, rebuilds the portal, and publishes the operating model, user guide, decision log and runbook to Confluence (.github/workflows/docs-to-confluence.yml, space ARCHITECTU). The Jira story moves to Done.
  7. Tell people. Changelog entry; a short note to the networks on the Community page.

Until the Jira and Confluence secrets are added to the repository, both workflows run as dry runs and log what they would do. See integrations/config.yaml.

5. Contributions and moderation

  • Members can add case studies, insights, resources, guidance and training to the library.
  • Every contribution is checked before it is public: no personal data, no named individuals without consent, accurate source links, plain English, and nothing that would identify an organisation's unpublished problems without its agreement.
  • Moderators publish, ask for changes or decline within 10 working days, and always say why.
  • Contributions are OGL v3 unless the contributor chooses otherwise.
  • Contributors keep credit as their organisation, or anonymously if they prefer.

6. Surveys and commissions

  • Any organisation can run a survey through the Commons. Each one shows the privacy notice first, never asks for names or emails, and shows results only as totals, with totals under 5 hidden.
  • Commissions (for example assessing a data asset, writing rules, a peer review of a data quality action plan, training or incident help) are triaged weekly. Anything needing an official decision goes to tier 3 with the requester's agreement.
  • The Commons tooling survey does not replace any official survey.

7. AI in the Commons

  • The portal assistant drafts rules, explains results and finds frameworks. A person always reviews what it produces before it is used.
  • Every AI component follows the route in the AI-for-DQ guidance: evaluate, assure (DPIA where personal data is involved, Algorithmic Transparency Recording Standard record), pilot, then reuse.
  • The rule-drafting evaluation (knowledge/ai-eval/) is rerun before any change to prompts or models is released.

8. Measures of success

  • Organisations using the kit or portal, by type and nation (from opt-in surveys, never tracking)
  • Critical assets with a measured baseline
  • Time from request to first answer; commissions completed
  • Accessibility issues open and their age
  • Share of contributions from outside central government
  • Portal task completion and ease scores from the feedback survey

Data quality management playbook

Data quality management playbook for critical data assets

Generated from knowledge/playbook.yaml by scripts/build_playbook_doc.py. Edit the YAML, not this file. Last reviewed 2026-10-30. Owner: Data quality lead (Commons). Content licence: OGL v3.0.

A repeatable way to know, prove and improve the quality of the data that matters most. Eight stages, from choosing your critical data to keeping it healthy year after year. Each stage has steps, outputs, a checklist, who does what, an inclusion check and the matching requirement in the UK DAM policy and elsewhere.

Interactive version: the portal page playbook.html has a checklist you can tick, template downloads and a jurisdiction finder.

Who it is for

  • UK government departments and arm's length bodies with critical data assets (mandatory under the DAM policy)
  • Devolved administrations, local government, the NHS, police and the third sector (voluntary adoption)
  • Crown Dependencies, Overseas Territories and international partners
  • Any organisation with data that many people or services depend on

Use it anywhere

Use your own words. The playbook works the same whatever your mandate calls things.

In this playbookYou might call it
Critical data asset (CDA)Critical data, key dataset, master or reference data, high-value dataset (EU), essential shared data asset (older UK term)
DAM policyYour data strategy, data governance policy, statistics code, regulator's rules or contract
Data quality action plan (DQAP)Data quality plan, improvement plan, quality assurance plan (Canada, Australia, US agencies)
Data ownerInformation asset owner, data custodian, accountable executive, business owner
CDA returnAnnual data inventory, asset register submission, catalogue record

If your context has no mandate, start at stage 1 and use the issues framework as your method. Nothing here depends on the UK policy.

Principles

  1. Fit for purpose. Quality means good enough for the decisions and services that rely on the data. Agree what 'good enough' means with the people who use it.
  2. Start with what matters. Focus on the few data items that drive important decisions, not every column.
  3. Measure, don't guess. Write rules down, test them automatically and keep the results. A score without a rule is an opinion.
  4. Fix causes, not symptoms. Cleaning data downstream hides the problem. Fix it where the data is created.
  5. Be open about limits. Publish what you know about quality, including what is wrong. Users trust honest data more than perfect-looking data.
  6. Include everyone. Check that quality is as good for every group of people the data describes. Missing or wrong data about some groups excludes them from services.
  7. Keep it going. Quality is a routine, not a project. Measure on a cycle, review every year and hand over cleanly.

The eight stages

Stage 1: Identify your critical data

Goal: Know which data assets are critical and which data items in them matter most. Typical effort: 1 to 3 days per asset.

Steps

  1. List data assets other teams, services or organisations depend on.
  2. Test each against your criteria. Under the DAM policy: shared value across government, open or restricted classification, serving one or more of the policy's purposes.
  3. Record each critical asset with an owner, a steward and the standard metadata properties.
  4. For each asset, name the 5 to 15 data items that drive the most important decisions (critical data elements).
  5. Record who uses the data, for what, and the people or places it describes.

Outputs: Critical data asset register; Critical data elements list per asset; User and purpose map.

Checklist

  • [ ] Every critical asset has a named owner and steward (roles, not just a team).
  • [ ] Metadata is complete enough for someone outside your team to find and understand the asset.
  • [ ] Critical data elements are agreed with at least two user teams.
  • [ ] You know which groups of people, places or organisations the data covers, and which it might miss.

Who leads: Data owner (A), Data steward (R).

UK DAM policy and DQAP:

  • DAM-1 Identify, record and centrally report shared critical data assets
  • DAM-2 Assign clear ownership and accountability for each data asset
  • DAM-4 Meet minimum standards for discoverability
  • DQAP-1 Identify critical data and the data items that matter most
  • CDA-M Record 13 metadata properties including creator, identifier, temporal coverage, conformsTo and security classification

Elsewhere: Comparable to: ISO 8000-61 (data quality planning), DAMA-DMBOK (critical data elements), Canada GC data quality guidance (identify key data), EU high-value datasets.

Inclusion check: Check the user map includes services for disabled people, people on low incomes, Welsh and other language users, and all four UK nations where relevant.

Toolkit: Describe the asset once and see gaps against the CDA metadata (weaver.html).

Stage 2: Define quality rules and targets

Goal: Turn 'good enough' into rules a computer can test, with agreed targets. Typical effort: 2 to 5 days per asset.

Steps

  1. For each critical data element, choose the dimensions that matter (completeness, uniqueness, consistency, timeliness, validity, accuracy).
  2. Write each rule in plain English first, then as a testable rule.
  3. Set a target for each rule using the importance of the purpose and the impact of failure (issues framework target ranges).
  4. Record the rules as a data contract so suppliers and users see the same promise.
  5. Agree targets with the data owner and the main users.

Outputs: Rule catalogue; Targets per rule; Data contract (ODCS).

Checklist

  • [ ] Every critical data element has at least one rule.
  • [ ] Every rule names its dimension, owner and target.
  • [ ] Targets come from user impact, not from what the data already achieves.
  • [ ] Rules are stored as files, not only in a tool, so they survive a change of supplier.

Who leads: Data owner (A), Data steward (R), Data quality lead or analyst (R).

UK DAM policy and DQAP:

  • DAM-3 Meet minimum standards for data quality through a DQAP or equivalent
  • DAM-5 Meet minimum standards for interoperability
  • DQAP-2 Identify data quality rules, dimensions and agreed thresholds
  • IF-1 Combined score = importance of purpose x impact of the issue
  • IF-2 Target ranges by combined score: 75-90, 90-97.5, 97.5-99.9, 99.9-100

Elsewhere: Comparable to: ISO/IEC 25012 (quality characteristics), ODCS v3.1 quality rules, W3C DQV, ESS and UN NQAF quality dimensions.

Inclusion check: Add rules for fields that affect fair treatment: completeness of protected characteristics where lawfully collected, valid address formats for all nations, names in all scripts.

Toolkit: Write rules in plain English with the assistant, then save them as a data contract (assistant.html).

Stage 3: Measure and set a baseline

Goal: Know where you are today. Typical effort: 1 to 3 days per asset.

Steps

  1. Profile the data to see patterns, gaps and outliers.
  2. Run every rule and record results with the date and data version.
  3. Log every failure as an issue with its dimension, size and affected users.
  4. Break results down by group (region, nation, age band, channel) where you lawfully can.
  5. Write the baseline into a short data quality statement.

Outputs: Baseline results; Issue log; First data quality statement.

Checklist

  • [ ] Results are reproducible (same rules, same data, same result).
  • [ ] Each issue says how many records and which users are affected.
  • [ ] You have looked for differences in quality between groups.
  • [ ] Results are stored where the next steward will find them.

Who leads: Data owner (A), Data steward (R), Data quality lead or analyst (R).

UK DAM policy and DQAP:

  • DQAP-3 Assess current quality, log issues and set a baseline

Elsewhere: Comparable to: ISO 8000-8 (measurement), IMF DQAF assessment, ABS data quality statements.

Inclusion check: If quality is worse for a group, record it as a separate issue so it is not averaged away.

Toolkit: Profile and check a file in your browser; nothing is uploaded (check.html).

Stage 4: Prioritise

Goal: Fix the issues that hurt most first. Typical effort: Half a day per cycle.

Steps

  1. Score each issue with the issues framework: importance of purpose times impact, then the band below target.
  2. Sort by priority. Critical issues are fixed immediately; high in one cycle; medium in three; low in six.
  3. Agree the order with the data owner. Record accepted risks explicitly.
  4. Turn the top issues into a data quality action plan with goals and dates.

Outputs: Prioritised issue list; Data quality action plan; Risk acceptances.

Checklist

  • [ ] Every issue has a priority score and a resolution timescale.
  • [ ] Accepted risks are signed by the data owner, with a review date.
  • [ ] The plan has measurable goals (rule X from 82% to 95% by a date).
  • [ ] Issues that affect some groups more than others are not ranked down because they are 'small'.

Who leads: Data owner (A), Data steward (R).

UK DAM policy and DQAP:

  • DQAP-4 Prioritise improvements and set goals using impact and risk
  • IF-3 Bands below target set a band score; priority = combined x band
  • IF-4 Resolution: Critical immediately; High 1 cycle; Medium 3; Low 6

Elsewhere: Comparable to: risk-based prioritisation in ISO 31000 and DAMA-DMBOK; US agency data quality plans.

Inclusion check: Weight impact by who is affected, not only how many: a small number of wrong records can stop someone getting a service.

Toolkit: Score and rank issues with the government method (guidance.html).

Stage 5: Find causes and fix at source

Goal: Stop problems coming back. Typical effort: Varies by cause.

Steps

  1. For each priority issue, ask why until you reach the cause (people, process, system, supplier, standard).
  2. Choose the fix closest to where the data is created. Prefer prevention (validation at entry, shared identifiers, code lists) over cleaning.
  3. Give each action an owner and a date. Put supplier actions into the contract or change request.
  4. Re-run the rules to prove the fix worked.

Outputs: Root cause records; Actions with owners; Evidence that fixes worked.

Checklist

  • [ ] Every fix is tested by re-running the rule.
  • [ ] Fixes at source are preferred; any downstream cleaning is recorded and temporary.
  • [ ] Supplier obligations are in the contract with a KPI.
  • [ ] Changes to forms or systems were tested with users, including assistive technology users.

Who leads: Data owner (A), Data steward (R), Data producer or system owner (R).

UK DAM policy and DQAP:

  • DQAP-5 Identify root causes, choose and own actions

Elsewhere: Comparable to: ISO 8000-61 improvement process, Plan-Do-Check-Act, Lean root cause analysis.

Inclusion check: Fix forms that force wrong answers (no 'prefer not to say', one-line names, UK-only postcodes). These cause bias at source.

Toolkit: Put data quality duties and KPIs into supplier contracts (commercial.html).

Stage 6: Report and be open

Goal: Users know how good the data is and what it can safely be used for. Typical effort: Half a day per cycle.

Steps

  1. Update the data quality statement each cycle: scores, trends, known issues and what the data should not be used for.
  2. Publish quality metadata with the asset (W3C DQV or the CDA return fields) so catalogues such as the National Data Library can show it.
  3. Report the portfolio to your governance board and the centre (for example the CDA return).
  4. Rate the asset with Q-FAIR (quality, findable, accessible, interoperable, reusable): record access route, standards, licence and provenance so the ratings can be shown.
  5. Tell affected users directly about critical issues.

Outputs: Data quality statement; Quality metadata; Portfolio report or CDA return.

Checklist

  • [ ] The statement is in plain English, accessible (WCAG 2.2 AA) and dated.
  • [ ] It says what the data is not fit for, not only what it is fit for.
  • [ ] Machine-readable quality metadata is published with the catalogue record.
  • [ ] Group differences in quality are reported, not hidden.

Who leads: Data owner (A), Data steward (R).

UK DAM policy and DQAP:

  • DAM-4 Meet minimum standards for discoverability
  • DQAP-6 Report quality to stakeholders, including limitations

Elsewhere: Comparable to: Code of Practice for Statistics (Quality pillar), ESS quality reports, ABS and Statistics Canada quality statements, W3C DQV.

Inclusion check: Test the statement with people outside the data team. Offer it in Welsh where required and in Easy Read where the data describes the public.

Toolkit: Export results as DQV and CDA return rows (pipeline.html).

Stage 7: Monitor and sustain

Goal: Quality stays good without heroics. Typical effort: Hours per month once set up.

Steps

  1. Run checks automatically on every new load or on a fixed cycle (monthly is a good start).
  2. Track trends; alert when a rule drops below its target.
  3. Escalate using agreed thresholds (see escalation).
  4. Build skills: train stewards and producers; share rules and lessons with other teams.
  5. Keep rules, results and the plan in version control so they survive staff and supplier changes.

Outputs: Automated checks; Trend dashboard; Escalation log; Training record.

Checklist

  • [ ] Checks run without manual effort.
  • [ ] Someone is alerted when quality drops, and knows what to do.
  • [ ] The steward role has a named deputy.
  • [ ] Rules and results are stored openly where licensing allows (MIT code, OGL content).

Who leads: Data owner (A), Data steward (R), Data producer or system owner (R), Data quality lead or analyst (R).

UK DAM policy and DQAP:

  • DQAP-7 Repeat measurement, track trends, refine rules

Elsewhere: Comparable to: data observability practice, ISO 8000-150 (roles), continual improvement in ISO 9001.

Inclusion check: Keep the group breakdowns in the monitoring, not just the baseline.

Toolkit: Schedule checks in a pipeline and watch the status (pipeline.html).

Stage 8: Review every year

Goal: The asset, rules and targets still match what users need. Typical effort: 1 day per asset per year.

Steps

  1. At least every 12 months, review the asset record, owner, rules, targets and plan.
  2. Ask users whether the data still meets their needs; add rules for new uses (for example AI training).
  3. Retire rules that no longer matter; raise targets that are now easy.
  4. Check maturity and set next year's goals.
  5. Submit the updated record or return.

Outputs: Annual review note; Updated register entry; Next year's goals.

Checklist

  • [ ] The review is dated and signed off by the data owner.
  • [ ] New uses (such as AI) have been assessed against the AI-ready data guidance.
  • [ ] The asset is still correctly classed as critical, or has been retired with a reason.
  • [ ] Lessons are shared with the Commons or your community.

Who leads: Data owner (A), Data steward (R).

UK DAM policy and DQAP:

  • DAM-6 Review asset records at least every 12 months

Elsewhere: Comparable to: annual statistical quality reviews, ISO 8000-61 review, management review in ISO 9001.

Inclusion check: Ask representatives of groups the data describes whether anything has changed for them.

Toolkit: Re-run the maturity self-assessment (maturity.html).

Co-design and contribution charter

_Generated from knowledge/build.yaml by scripts/gen_community_docs.py. Edit the YAML, not this file._

We build the Commons with the people who use it, so it meets real needs, includes everyone and stays a public good.

Principles

  • Open by default. Code is MIT, content is OGL v3.0. Decisions, roadmap and backlog are public.
  • Nothing about us without us. People affected by data, including people who are often left out, help shape what we build.
  • Plain English. We write for everyone. Jargon is explained or removed.
  • Accessible to all. We aim for WCAG 2.2 AA, test with assistive technology, and offer alternatives for every activity.
  • Privacy first. We never need your name or email. Contributions credit organisations, or nobody.
  • Evidence over opinion. Claims link to sources. Unchecked claims are labelled.
  • Fair participation. Sessions rotate times and formats, so different time zones, caring responsibilities and working patterns can take part.
  • Transparent decisions. Votes inform priority; the product owner decides and records why in the decision log.

House rules

  • Be respectful and constructive. Follow the code of conduct.
  • No personal data: no names, emails, phone numbers or identifiers of real people, unless it's your own organisation's public contact route.
  • No official-sensitive or classified material. If in doubt, leave it out.
  • No advertising or selling. Suppliers are welcome to share evidence and open resources, not sales material.
  • Cite your sources and say what you haven't checked.
  • Only share what you have the right to share, under an open licence.
  • AI-assisted content is welcome if you say so and a person has checked it.

Guidelines

  • Describe the problem and who has it before suggesting a solution.
  • Keep contributions short. Link to longer documents.
  • Use the issue forms on GitHub, or the forms here, so we have what we need.
  • One idea per suggestion, so people can vote on it.
  • Say which nation, sector or jurisdiction your contribution applies to.

Safeguards

  • Moderation. Every contribution is checked before it's public: no personal data, accurate links, plain English, an open licence.
  • Automatic personal data checks. Forms block obvious emails, phone numbers, National Insurance and NHS numbers before anything is sent.
  • Small numbers hidden. Survey and benchmark results show totals only, and hide groups under 5.
  • No tracking. No analytics, cookies or third-party trackers. Fonts are the only external request.
  • Masked contact. Contact is through a form. The team's email address is never shown, to prevent spam and impersonation.
  • Security reports in private. Security problems go through GitHub private vulnerability reporting, never public issues.
  • Right to withdraw. Ask through the contact form and we'll remove your contribution.
  • Safeguarding. Content about vulnerable people must be about data and services, never about identifiable individuals.
  • Conflicts of interest. Contributors say if they work for a supplier of a product they're discussing.
  • Escalation. Concerns about conduct or content go to the moderators through the contact form; they reply within 5 working days.

Decision log (this repository)

2026-11-03 · D-GH-01 · GitHub is the working system behind every portal feature

  • Decision: each portal feature maps to a GitHub feature (map on github.html). Forms that save on claude.ai open the matching GitHub issue form or discussion, pre-filled, everywhere else (window.DQP_GITHUB in the shell). The roadmap is computed from backlog statuses and mirrored as milestones by scripts/backlog_to_issues.py --sync with the same rule. The portal build reads public issue data once (issue numbers, states, thumbs-up votes, wishlist) with a read-only token; visitors' browsers never call GitHub (D-POL-01). Release tags stay a person's decision: the release workflow runs when a maintainer pushes a tag.
  • Why: the portal described processes (roadmap, votes, co-design, releases) that only fully worked on claude.ai or existed only on paper. GitHub already offers forms, reactions, milestones, discussions, releases and Actions, so the Commons uses them rather than building its own.
  • Alternatives considered: GitHub Projects board (left for later: user-owned projects need a personal token, which the Commons doesn't hold); calling the GitHub API from the browser (rejected: third-party requests and rate limits); creating tags automatically from the release record (rejected: releasing stays a deliberate human step).

2026-11-03 · D-REPO-01 · No decks or films in the repository unless explicitly allowed

  • Decision: slide decks and video files are ignored by .gitignore and refused by tests/test_repo_policy.py, unless their path is listed in .media-allowlist.
  • Why: the project lead's standing rule. They are large, hard to review and hard to make accessible, and they belong where they are presented.
  • Alternatives considered: Git LFS (rejected: the content still doesn't belong here); a size limit only (rejected: small decks would slip through).

2026-11-03 · D-REPO-02 · Contact by form only, everywhere

  • Decision: the only way to reach the Commons is the contact form (a GitHub issue form, 0-contact.yml, pre-filled from the portal). No email address appears in any page, document, data file or template; the case study template asks for a contact route, not a name and email. A test fails on any email address other than GitHub's no-reply addresses.
  • Why: the project lead's standing rule; publishing addresses invites spam and exposes people; one route is easier to moderate and measure.
  • Alternatives considered: a shared team inbox (rejected: still an address to publish and a single person's burden); a third-party form service (rejected: D-POL-01, no third-party requests).

2026-11-03 · D-REPO-03 · Scan for credentials, private links and marking banners, with a self-test

  • Decision: tests/test_repo_policy.py refuses tokens and keys, links to private claude.ai chats, projects or artifacts, and protective marking banners, and plants one example of each to prove the scan works. A weekly Repository health workflow compares settings with .github/settings-baseline.json and reports drift without changing anything.
  • Why: adapted from the GitHub Repos Asset Catalogue, which uses the same patterns; the repository is public, so prevention must be automatic.
  • Alternatives considered: rely on GitHub secret scanning alone (kept as well, but it doesn't cover private links or markings).

2026-11-03 · D-TK-02 · The toolkit reads numbers with its own rule

  • Decision: dqkit/numbers.py reads numbers from text (optional spaces and sign, digits with optional point, optional exponent, "inf"), giving the correctly rounded value; engine.js uses the same rule. pandas is no longer used for this, so the <3.1 cap (D-CI-01) is lifted to <4.
  • Why: pandas 3.1 changed its parser, which made results depend on the installed pandas version and broke parity. Owning the rule makes Python and the browser agree on every pandas version. Issue #25.
  • Alternatives considered: copy pandas 3.1's parser into JavaScript (rejected: results would differ again for anyone on pandas 3.0, and again at the next change).

2026-11-03 · D-UX-01 · Page drawer, collapsible sections, change flags and portal search

  • Decision: every page gets an "On this page" drawer built from its headings, collapsible sections, and New or Updated flags for sections that differ from the previous release (fingerprints in portal/section-baseline.json, regenerated at each release by scripts/section_baseline.py). Search covers pages, sections and named items in the knowledge base; its index (search-index.js) loads only when search is first opened. Motion is used only for content coming into view, never hides content already on screen, and is off for anyone who prefers reduced motion.
  • Why: pages are long; the menu helps across the portal but not within a page. Flags show returning readers what changed without reading release notes.
  • Alternatives considered: a server-side search service (rejected: D-POL-01 and cost); flags typed by hand (rejected: they would be forgotten); a fixed side table of contents (rejected: takes width from tables on smaller screens).

2026-11-03 · D-WV-02 · Application profiles in the Weaver are simplified shapes, not full SHACL

  • Decision: the Weaver checks the DCAT output against simplified must/should property lists for DCAT-AP 3, GeoDCAT-AP, StatDCAT-AP and the UK critical data asset properties, plus ISO 8601 dates, in both engines. It says plainly to validate with the official SHACL shapes before publishing.
  • Why: a full SHACL engine in the browser is heavy; the common gaps are missing properties and bad dates, which these checks catch. Issues #11 and #13.
  • Alternatives considered: bundle a SHACL validator (rejected for now: size and a third-party dependency); skip the check (rejected: users asked to know if they meet a profile).

2026-11-03 · D-OPS-02 · Weekly maintenance by a scheduled task, with people-dependent work kept open

  • Decision: a weekly scheduled task (Monday mornings, London time) reviews CI, open issues, Dependabot pull requests, content health and settings drift, fixes what it safely can, and reports the rest. Backlog items that need people (user research, independent audit, translation, live co-design, tenant trials, checks with statistics offices) are prepared in full and kept open.
  • Why: the project lead handed over ongoing maintenance; closing items that need people would overstate what is done.
  • Alternatives considered: close prepared items (rejected: misleading); daily runs (rejected: too noisy for the volume).

2026-11-03 · D-POL-03 · Version 2.0.0, not 1.7.0

  • Decision: release as 2.0.0.
  • Why: the release policy treats removing files, links or commands people rely on as a major change; this release removes dqkit survey, two documents and some page anchors.

2026-11-03 · D-POL-02 · Keep the public repository to published or original material; hold the rest privately

  • Decision: remove from the public repository and portal: content drawn from documents shared privately and not published by their owners; internal tooling work and our critique of it; unsent draft messages; unconfirmed dates from an internal timeline; advice framed for the CDO Council and GDS; figures from the internal register prototype. The removed material is kept in a private bundle for a private repository, and the public git history is rewritten to drop it.
  • Why: the repository became public on 2 November. Republishing or critiquing others' unpublished work in public breaks trust and handling expectations; unconfirmed dates presented as fact mislead; advice to a governance body should reach it first, privately.
  • Kept, with credit and flagged for the owners' permission: the trust level (adapted from the IOPC's approach), the DQAP route for data you produce or receive (from a community decision tree), the case study drafter and the workbook's suggested RACI. These embody general methods rather than reproduce documents, and removing them would break the CDA return format.
  • Alternatives considered: remove everything derived from those sources (rejected for this release: breaks outputs people use; revisit once owners respond); keep all and add caveats (rejected: does not address handling).

2026-11-03 · D-POL-01 · No third-party requests from the portal

  • Decision: bundle js-yaml (4.2.0, MIT) into the build and remove Google Fonts; pages use system fonts.
  • Why: many government networks block CDNs, which broke the check page's rules reader with a misleading error; and font and script CDNs see every visitor's IP address, which conflicts with the privacy promise that nothing leaves the device.
  • Alternatives considered: self-host the web fonts (possible later; adds files and licences to manage).

2026-11-03 · D-IA-01 · Menu in journey order with levels

  • Decision: six groups in the order people work: 1 Start, 2 Learn, 3 Check, 4 Improve, 5 Apply, 6 Contribute. Every page carries a level (Beginner, Intermediate, Advanced) shown as a badge; the breadcrumb follows the group automatically. The home page and README offer three journeys.
  • Why: the old groups (Start, Do, Know, Govern, Scenarios, Community) mixed task types with topics, so newcomers had no obvious path and experts had to hunt. Levels match the three-level scales used by APS, Canada, JNCC and others (see professions.html).
  • Alternatives considered: persona-first menu (kept as routes on Home and For your role); level-first menu (splits related pages apart).

2026-11-03 · D-PRO-01 · Map data quality across professions from sources read on the day

  • Decision: knowledge/professions.yaml records, for each profession or framework, only what its source says (checked 3 November 2026), plus the Commons' mapping to 12 capabilities, marked as an interpretation.
  • Why: senior audiences will rely on it; each claim needs to stand up. The research found no standalone data quality skill in the GDaD framework, which is itself a useful finding.

2026-11-02 · D-CI-04 · Security scanning and a public health score

  • Decision: add CodeQL (Python, JavaScript, Actions; security-and-quality queries) and OpenSSF Scorecard workflows. Add Dependabot for pip and GitHub Actions, grouped into one weekly pull request each, plus CODEOWNERS.
  • Why: the repository is now public and meant for reuse across government. Departments assessing it need visible, independent evidence that it is maintained securely. Automation keeps it current without manual checking.
  • Dependabot range rule: increase-if-necessary for pip. The default raised every minimum to the newest release (PR #28), which would lock out departments on older, centrally managed environments with no benefit, since CI already installs the newest allowed versions.
  • Alternatives considered: GitHub's one-click CodeQL "default setup" (equivalent, but needs a settings change this session cannot make, and is less visible in the repository).

2026-11-02 · D-CI-03 · Root LICENSE is the exact MIT text; OGL statement moves to docs/CONTENT-LICENCE.md

  • Decision: remove the appended OGL paragraph from LICENSE; state the content licence in docs/CONTENT-LICENCE.md and link it from the README.
  • Why: GitHub showed the licence as "NOASSERTION" (unknown), because it only recognises an exact licence text. An unlabelled licence discourages reuse and hides the repo from licence-filtered searches.
  • Alternatives considered: keeping one combined file (rejected: GitHub cannot detect it); a second root LICENSE-OGL file (rejected: two root licence files can also confuse detection).

2026-11-02 · D-CI-02 · Move GitHub Actions to Node 24 releases

  • Decision: checkout, setup-python, setup-node, upload-artifact v7; upload-pages-artifact and deploy-pages v5; github-script v8 (same scripting interface as v7); Node 22 for the checks. Dependabot keeps them current from now on.
  • Why: every run warned that Node 20 actions are deprecated and being forced onto Node 24; Node 20 itself is end of life.

2026-11-02 · D-CI-01 · Cap pandas below 3.1 until the browser engine is re-aligned

  • Decision: pandas>=2.0,<3.1 in requirements.txt and pyproject.toml; Dependabot ignores pandas 3.1+. Add odfpy (OpenDocument spreadsheets) as a declared dependency.
  • Why: on the first GitHub run, CI installed pandas 3.1.0, which parses numbers precisely (for example "0.30000000000000004" stays as written).
